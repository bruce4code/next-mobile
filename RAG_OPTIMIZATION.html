RAG 优化实战：从"能用"到"好用"的蜕变

背景

上篇文章分享了从零到1构建 RAG 系统的过程，系统跑起来之后，我开始思考一个问题：它能用，但真的好用吗？

在实际使用中，我发现了一些痛点：

  • 相似度阈值：搜索结果经常包含一堆低相关的文档，干扰 AI 判断
  • 关键词提取：文本搜索降级时的关键词提取靠手工维护词典，覆盖不全
  • RAG 上下文位置：长对话中，LLM 注意力被大量聊天历史分散，知识库内容被"冲淡"
  • 用户提问方式：用户不会用"精准关键词"提问，经常说"怎么退？""坏了怎么办"这类模糊问题

这篇文章记录了我对 RAG 系统进行的一系列优化实践，希望能给同样在打磨 RAG 的朋友一些参考。

优化一：Prompt 优化 + 相似度阈值

问题

最初的 Prompt 设计很啰嗦：

【重要指令】你必须优先使用以下知识库中的信息来回答用户的问题！
【知识库参考资料】
...
【强制回答规则】
1. 🔴 必须首先尝试使用知识库中的信息回答
2. 🟢 ...

实际测试发现，LLM 对这类"用力过猛"的指令反而容易"过度服从"——即使文档完全不相关，它也会强行从文档中编造答案。

同时，向量搜索返回的所有结果都一股脑塞进去，相似度 20% 的文档也在凑数。

解决方案

1. 简化 Prompt

export function buildRAGContext(documents) {
  const context = documents
    .map((doc, index) => {
      const relevance = doc.similarity !== undefined
        ? ` (相关度: ${(doc.similarity * 100).toFixed(0)}%)`
        : ''
      return `[文档${index + 1}] ${doc.title}${relevance}\n${doc.content}`
    })
    .join('\n\n---\n\n')

  return `你是电商AI助手，请严格基于以下知识库文档回答用户问题。

## 知识库文档
${context}

## 回答要求
1. 必须注明引用来源，格式：[来源：文档名]
2. 如果所有文档都与用户问题无关，回复"知识库中暂无相关信息，请补充相关文档后再试"
3. 回答简洁准确，不编造文档中没有的内容`
}

改动要点：

  • 把"用力过猛"的指令改成简洁清晰的要求
  • 明确要求"不编造文档中没有的内容"
  • 要求注明引用来源，方便追溯
  • 当文档无关时直接告知用户，而不是强行回答

2. 引入相似度阈值

const DEFAULT_MIN_SIMILARITY = 0.35

只有相似度 >= 0.35 的文档才进入上下文。这个值怎么定的？

  • 我跑了几十条真实用户问题，观察向量搜索返回的相似度分布
  • 大部分真正相关的文档相似度在 0.4~0.7 之间
  • 0.3 以下的几乎都是无关文档
  • 0.35 是一个比较安全的阈值——既不漏掉相关文档，又能过滤大部分噪音

3. 粗召回 + 阈值过滤

还有一个关键细节：搜索时先多拉一些文档，再按阈值过滤，而不是直接限制 topK。

const VECTOR_RECALL_MULTIPLIER = 3

// 粗召回：多拉一些文档，给阈值过滤留空间
const recallCount = topK * VECTOR_RECALL_MULTIPLIER

// 搜索...
// 然后按阈值过滤
const filtered = results.filter((r) => r.similarity >= minSimilarity)
const finalResults = filtered.slice(0, topK)
💡 举个例子：

假设用户问"怎么申请退款"，向量搜索可能把"退款政策"（相似度 0.52）、"物流查询"（相似度 0.28）、"退货流程"（相似度 0.42）都召回来。如果只取 top3，会把相似度 0.28 的物流文档也塞进去。粗召回 9 条再过滤，只保留 >= 0.35 的，最终只取 top5，质量明显提升。

效果对比

指标 优化前 优化后
上下文噪音 可能包含 0.2 相似度的无关文档 全部 >= 0.35
AI 编造答案 经常发生 显著减少
答案引用来源 无 清晰标注文档来源
未找到信息时 强行回答 告知用户补充文档

优化二：文本搜索降级策略

问题

向量搜索依赖 embedding API，但 API 可能超时、限流或临时不可用。最初的做法是直接报错，用户体验很差。

解决方案

当向量搜索失败或所有结果都被阈值过滤掉时，自动降级为文本搜索（关键词匹配）。

try {
  queryEmbedding = await generateEmbedding(query)
} catch (embeddingError) {
  console.warn('⚠️ 无法生成查询 embedding，尝试文本搜索:', embeddingError)
  return await searchByText(query, options)
}

这里的关键是关键词提取。最初的实现是一个手工维护的电商词典 + 正向最大匹配算法：

const DICT = [
  '退换货', '退款', '订单', '物流', '苹果', '火龙果', ...
].sort((a, b) => b.length - a.length)

function extractKeywords(text: string): string[] {
  // 正向最大匹配...
}
⚠️ 这个方案的问题很明显：
  • 词典维护成本高：每新增一个商品品类（比如"榴莲"），都要手动添加
  • 无法处理未登录词：用户说"这个果子坏了"，词典里有"水果"没有"果子"，识别不出来
  • 分词粒度不准确："退换货政策"会匹配"退换货"，但"退货申请流程"就乱了

优化：从手工词典到 nodejieba

经过调研，我决定使用结巴分词的 Node.js 原生版本 —— nodejieba。

import * as jieba from 'nodejieba'

function extractKeywords(text: string): string[] {
  const keywords = jieba.extract(text, 5)
  return keywords
    .map(k => k.word)
    .filter(word => word.length > 0 && !STOP_WORDS.has(word) && !/^\d+$/.test(word))
}

nodejieba 使用 TF-IDF 算法提取关键词，效果：

退换货政策是什么 → 退换货, 政策
如何申请退款 → 退款, 申请
苹果多少钱一斤 → 一斤, 苹果
订单物流在哪里查 → 订单, 物流
怎么联系客服 → 客服, 联系
优惠券怎么用 → 优惠券
为什么水果坏了 → 水果
我想退掉这个火龙果 → 火龙果, 退掉
💡 对比效果：

词典方案："为什么水果坏了" → 什么, 水果, 坏了（"为什么"被当成关键词）

nodejieba TF-IDF："为什么水果坏了" → 水果（"为什么"被 TF-IDF 自动降权）

安装 nodejieba 的坑

nodejieba 是 C++ 原生模块，安装时需要编译。用 pnpm 安装时默认跳过了编译脚本，需要额外两步：

# 1. 安装依赖
pnpm add nodejieba

# 2. 下载/编译原生绑定
cd node_modules/nodejieba && npx @mapbox/node-pre-gyp install --fallback-to-build

关键是第二步。nodejieba 使用了 @mapbox/node-pre-gyp，它会先尝试下载预编译的二进制文件（nodejieba-v3.5.8-node-v115-darwin-arm64-unknown.tar.gz），如果下载失败则回退到从源码编译（需要 cmake）。

优化三：RAG 上下文位置优化

问题

最初的设计把 RAG 上下文放在消息列表的最前面：

[system: RAG 上下文]
[user: 之前的对话历史...]
[assistant: ...]
[user: 当前问题]

但在长对话中，LLM 的注意力集中在最近的几条消息上，前面的 RAG 上下文容易被"冲淡"。测试发现，当对话超过 10 轮后，LLM 经常忽略知识库内容，开始用自己的知识回答。

解决方案

把 RAG 上下文插入到用户最后一条消息之前：

const lastUserIndex = messages.findLastIndex((msg) => msg.role === 'user')
if (lastUserIndex >= 0) {
  enhancedMessages = [
    ...messages.slice(0, lastUserIndex),
    { role: 'system', content: ragContext },
    ...messages.slice(lastUserIndex),
  ]
}

调整后的消息顺序：

[user: 之前的对话历史...]
[assistant: ...]
[system: RAG 上下文]     ← 插在这里
[user: 当前问题]
✅ 效果：RAG 上下文紧挨着当前问题，LLM 在处理时会把二者放在一起理解，效果明显提升。

效果对比

对话轮数 优化前（RAG 在最前面） 优化后（RAG 在最后一条消息前）
1-3 轮 ✅ 很好 ✅ 很好
5-8 轮 ⚠️ 偶尔忽略知识库 ✅ 稳定引用
10+ 轮 ❌ 经常忽略 ✅ 仍然稳定

优化四：相似度阈值动态调整思路

目前使用的是固定阈值 0.35，但在实际使用中我发现：

  • 不同品类的最佳阈值不同：标准化的政策文档（如退换货政策）相似度通常较高（0.5+），而灵活的问答文档（如"怎么联系客服"）相似度可能偏低（0.3~0.4）
  • 不同查询的语义粒度不同："退货"这种具体查询容易匹配，"帮我看看"这种模糊查询很难匹配

未来的优化方向：

  • 根据文档类型动态调整阈值
  • 或者根据查询的关键词数量和质量调整召回策略

优化五：停用词过滤

问题

即使用了 nodejieba，一些高频无意义词还是可能混入关键词列表。例如用户说"查一下订单"，nodejieba 可能提取出"查一下"和"订单"，但"查一下"对搜索没有帮助。

解决方案

保留一个精简的停用词表作为兜底过滤：

const STOP_WORDS = new Set([
  '的', '了', '在', '是', '我', '你',
  '吗', '呢', '吧', '啊', '呀',
  '查', '一下', '一下下',
  // ... 其他停用词
])

在 nodejieba 提取关键词后，再经过停用词过滤：

const keywords = jieba.extract(text, 5)
return keywords
  .map(k => k.word)
  .filter(word => word.length > 0 && !STOP_WORDS.has(word) && !/^\d+$/.test(word))
💡 注意：nodejieba 的 TF-IDF 算法已经内置了停用词过滤，这里的停用词表只是"双保险"，防止极个别情况下 TF-IDF 权重异常的词混入。

总结与心得

这次优化让我深刻体会到几个道理：

1. RAG 不只是"搜索 + 拼接"

很多人以为 RAG 就是把文档搜出来拼在一起扔给 LLM。实际远不止如此：

  • 搜索质量决定 RAG 的上限
  • 阈值过滤决定进入上下文的文档质量
  • Prompt 设计影响 LLM 如何理解和使用这些文档
  • 上下文位置影响 LLM 的注意力分配

2. 好的降级策略比完美的主方案更重要

向量搜索 API 可能随时不可用（超时、限流、模型下线）。一个稳健的 RAG 系统必须有降级策略：

向量搜索 → 失败 → 文本搜索（TF-IDF 关键词）

文本搜索 → 失败 → 告知用户补充文档

3. 关键词提取是文本搜索的核心

文本搜索看起来很"土"，但在很多场景下比向量搜索更可靠。而文本搜索的质量完全取决于关键词提取的质量。从手工词典到 nodejieba 的升级，是这次优化中收益最大的改动之一。

下一步优化方向

  • ✅ 文档分块（chunking）：长文档拆分成小段，每段独立 embedding（已实现）
  • ⬜ 混合搜索（向量 + 关键词权重融合）
  • ✅ embedding 缓存：基于 Supabase 数据库持久化（已实现）
  • ⬜ 动态阈值：根据查询类型自动调整相似度阈值
  • ⬜ RAG 可视化调试工具
从"能用"到"好用"，中间隔了无数个细节优化。希望这篇文章能帮你少走一些弯路。
