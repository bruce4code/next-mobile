> 一个从零搭建的生产级 AI 客服系统，核心是**混合检索 RAG 引擎**，配套了 Embedding 缓存、LLM Reranker、SSE 流式响应、模型 Fallback 链、全链路可观测性和自动化评测系统。

## 二、核心技术亮点

### 亮点 1：混合检索（Hybrid Search）— 最亮眼的技术点

**核心文件：** [src/lib/rag.ts](file:///Users/linruitao/Documents/100-study/200-reactjs/next-mobile/src/lib/rag.ts)

实现了一套完整的**向量 + 关键词混合检索系统**：

> **面试话术：** 我实现了一个混合检索 RAG 系统，核心流程是：用户提问 → 关键词提取 → 并行执行向量搜索和 BM25 风格关键词搜索 → RRF 融合排序 → 可选的 LLM Reranker 精排 → 构建上下文注入 LLM。

#### 技术细节

| 组件 | 实现方式 |
|------|----------|
| **向量检索** | 使用 OpenRouter 的 Embedding API（`qwen/qwen3-embedding-8b`）生成 1536 维向量，通过 PostgreSQL 的 `pgvector` 扩展做余弦相似度搜索（`<=>` 运算符） |
| **关键词检索** | 基于 `@node-rs/jieba`（N-API 原生分词器，性能优于纯 JS 方案）实现 TF-IDF 关键词提取 + BM25 风格评分，支持 title 加权（title 匹配 ×3 分） |
| **RRF 融合**（Reciprocal Rank Fusion） | `1/(K+rank)` 公式合并两路结果，K=60 时 keyword 权重更高，适合中文电商场景 |
| **LLM Reranker** | 当候选数 > 最终需要数时，调用 LLM 对每个文档打 relevance 分（0-10），用语义理解能力做精排 |
| **三级降级策略** | jieba 提取不到关键词 → ILIKE 原文兜底 → 空结果时返回"知识库暂无相关信息" |

#### 为什么这个设计优秀

- **向量搜索**捕获语义相似但字面不同的查询（如"电脑"和"笔记本电脑"）
- **关键词搜索**捕获精确术语匹配（如商品型号"ABC-123"）
- **RRF 融合**无需调权重参数，天然鲁棒
- **LLM Reranker**在最后一步用语义理解筛掉不相关内容

### 亮点 2：Embedding 缓存系统

**核心文件：** [src/lib/embedding.ts](file:///Users/linruitao/Documents/100-study/200-reactjs/next-mobile/src/lib/embedding.ts)

实现了**数据库级别的 Embedding 缓存**：

> **面试话术：** 我设计了一个 Embedding 缓存层，用文本 MD5 哈希 + 模型名作为唯一键存入 PostgreSQL，避免重复调用昂贵的 Embedding API。同时支持批量生成 embedding，配合 Prisma 的 `$transaction` 保证原子性。

- MD5 哈希去重，`ON CONFLICT DO NOTHING` 防止重复写入
- 1536 维向量校验，缓存数据异常时自动回退到 API 调用
- 批量 + 事务：多个 chunk 的 embedding 用 `$transaction` 批量插入，一个失败全部回滚

**核心文件：** [src/lib/chunking.ts](file:///Users/linruitao/Documents/100-study/200-reactjs/next-mobile/src/lib/chunking.ts)

使用 LangChain 的 TextSplitter：

> **面试话术：** 我根据文档类型做了差异化分块——Markdown 用 `MarkdownTextSplitter` 保留标题层级，纯文本用 `RecursiveCharacterTextSplitter`。chunk_size=300、overlap=50，并自动提取 Markdown 标题作为层级标签（如"退换货政策 > 邮费说明"），提升检索时的上下文理解。

### 亮点 4：SSE 流式响应 + 模型 Fallback 链

**核心文件：** [src/app/api/chat/route.ts](file:///Users/linruitao/Documents/100-study/200-reactjs/next-mobile/src/app/api/chat/route.ts)

> **面试话术：** 我实现了基于 SSE 的流式响应，用 `TransformStream` 管道处理 OpenRouter 的原始 SSE 帧，在每个 chunk 中注入实际使用的模型名。同时设计了模型 fallback 链——当主模型失败时自动切换到备选模型，遇到 401/403 认证错误则停止重试，避免无效请求消耗配额。

- `TransformStream` + `pipeThrough` 实现零拷贝的 SSE 转换
- 模型候选列表从环境变量 `OPENROUTER_MODEL` 动态读取，支持逗号分隔多模型
- `isAuthOrKeyError` 判断：Auth 错误直接 break，不再重试下一个模型
- 最终返回 502 时附带所有失败模型的错误信息，方便排查

### 亮点 5：LangSmith 全链路可观测性

> **面试话术：** 我用 LangSmith 做了三层可观测性：
> 1. `wrapOpenAI` 自动追踪所有 LLM 调用（包括 embedding 和 chat）
> 2. 在 API 路由中为每个请求生成 `requestId` 并关联 `userId`，方便在 Dashboard 按用户/请求筛选 trace
> 3. 搭建了自动化评测系统，用 `evaluate()` API 生成 Experiment，支持跨版本对比

**评测系统**（[eval/run-experiment.ts](file:///Users/linruitao/Documents/100-study/200-reactjs/next-mobile/eval/run-experiment.ts)）：
- 16 条测试用例覆盖产品、政策、FAQ 等类型
- 自定义 qualityEvaluator：正确性、相关性、忠实度三维评分
- LLM-as-Judge 评估：用另一个 LLM 对回答打分
- 支持快速模式（直接调 LLM）和完整模式（调本地 API + RAG 链路）

**核心文件：** [src/middleware.ts](file:///Users/linruitao/Documents/100-study/200-reactjs/next-mobile/src/middleware.ts)，[src/lib/i18n.server.ts](file:///Users/linruitao/Documents/100-study/200-reactjs/next-mobile/src/lib/i18n.server.ts)

### 亮点 7：数据库设计

**核心文件：** [prisma/schema.prisma](file:///Users/linruitao/Documents/100-study/200-reactjs/next-mobile/prisma/schema.prisma)

- **Document + DocumentChunk 双层模型**：文档级别存储元数据，chunk 级别存储向量和内容，通过 `documentId` 关联
- **pgvector(1536)**：使用 PostgreSQL 原生向量扩展，无需额外部署向量数据库（如 Pinecone、Weaviate）
- **EmbeddingCache 表**：`(textHash, model)` 唯一约束 + 索引，命中时直接返回缓存向量
- **OpenRouterChat 表**：`(conversationId, createdAt)` 复合索引，支持按对话查询历史
- **结构化日志**（[src/lib/logger.ts](file:///Users/linruitao/Documents/100-study/200-reactjs/next-mobile/src/lib/logger.ts)）：`[时间戳] [级别] [标签]` 格式，便于日志聚合和问题排查

### 一次对话请求的完整链路

1. 用户发送消息
2. `/api/chat` 接收请求，传入最后 10 条消息作为上下文
3. 判断是闲聊还是知识库问题
4. 若是知识库问题 → RAG 引擎执行混合检索
5. 检索结果 + 历史消息 → 构建 Prompt
6. 调用 OpenRouter（流式）→ SSE 返回给客户端
7. 整个过程被 LangSmith 自动追踪

## 四、面试高频问题 + 回答思路

| 面试问题 | 回答要点 |
|----------|----------|
| "为什么用 pgvector 而不是 Pinecone？" | 减少基础设施复杂度，PostgreSQL 一个数据库搞定业务数据 + 向量存储；事务保证一致性；已有 Prisma 生态；中小规模场景够用，成本低 |
| "RAG 如何避免 LLM 幻觉？" | ① RRF 融合关键词 + 向量两路召回提高检索质量 ② LLM Reranker 精排筛掉无关内容 ③ System prompt 强制要求引用来源 ④ "不知道就坦诚告知"指令 ⑤ 闲聊检测自动跳过 RAG |
| "如何处理高并发？" | Embedding 缓存减少 API 调用；maxConcurrency: 1 控制评测并发；可扩展方案：Redis 缓存层、pgvector 索引优化、DB 连接池调整 |
| "SSE vs WebSocket？" | SSE 足够（单向推送），实现简单，HTTP/2 多路复用，Vercel Edge 天然支持。WebSocket 适用于双向实时通信（如协同编辑），本项目中无此需求 |
| "为什么用 @node-rs/jieba？" | N-API 原生模块，性能比纯 JS 分词器快数倍；比 nodejieba 兼容性更好，支持 Vercel Serverless 部署 |
| "LangSmith 的价值？" | ① 全链路 trace 快速定位问题 ② Experiment 对比每次优化效果 ③ LLM-as-Judge 自动化评测 ④ 不用自建 Dashboard |
| "混合检索为什么比纯向量搜索好？" | 纯向量搜索在精确术语匹配上表现差（如商品型号 "ABC-123"），关键词搜索恰好弥补。电商场景中用户常问具体产品名、订单号，两路互补更可靠 |
| "为什么用 TransformStream 处理 SSE？" | 零拷贝，不阻塞主线程，天然适配 Vercel Edge Runtime 流式响应 |
| "你是怎么保证评测结果的可靠性的？" | 评测数据人工标注，覆盖多类型（产品、政策、FAQ）；使用 LLM-as-Judge 三维打分（正确性、相关性、忠实度）；每轮优化后跑完整 Experiment 对比 |

## 六、值得关注的工程细节

### 6.1 Vercel 部署中的原生模块处理

`@node-js/jieba` 包含 `.node` 原生二进制文件，需在 `next.config.ts` 中配置 `serverExternalPackages: ['@node-rs/jieba']`，否则 webpack/turbopack 会尝试将其打包进 JS bundle，导致 `.node` 文件解析失败。

### 6.2 闲聊检测

通过关键词匹配（"你好""谢谢""再见"等）判断是否为闲聊，闲聊直接走 LLM 不检索知识库，避免浪费配额和产生无意义的数据库查询。

### 6.3 评测系统的双模式设计

- **快速模式**：直接用 OpenAI SDK 调 LLM，不经过本地 API，适合快速验证模型响应质量
- **完整模式**：调本地 API + 完整 RAG 链路，需要数据库和认证 Cookie，适合验证真实业务场景
